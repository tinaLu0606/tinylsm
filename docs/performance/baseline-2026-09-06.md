# TinyLSM pre-optimization performance baseline

Status: complete on macOS and the fixed Linux VM.

This is the baseline before performance-focused development. It is intended to
make later changes measurable, not to claim that TinyLSM is competitive with a
production engine. No performance threshold is enforced in CI at this stage.

## Basic-scope closure decision

The original learning-engine scope can close here. TinyLSM now has a durable
WAL-first write path, crash-atomic batches, recovery-compatible versioned WAL,
ordered MemTable/SSTable reads and scans, Manifest publication, repeated flush,
full compaction, binary-safe CLI/API behavior, global serialized handle safety,
fault-injection coverage, and a live diagnostic Lab. The 97-test sanitizer and
Linux evidence below covers the newly added correctness boundaries.

This is not a production-readiness claim. Packaging, snapshots/transactions,
multi-level or background compaction, caches/filters, finer-grained concurrency,
and tail-latency/resource measurement remain intentionally outside the basic
scope. They are now optimization or expansion work and should be justified by
the baseline rather than treated as blockers for closing the original feature
phase.

## What was measured

The Release benchmark executable uses deterministic 16-byte keys, 100-byte
values, a fresh temporary database per repetition, and five repetitions per
case. Reported throughput below is the wall-time median. CV is the coefficient
of variation of throughput across the five samples.

The common TinyLSM/LevelDB cases are:

- sequential writes with WAL sync disabled: 100,000 operations;
- sequential writes with WAL sync enabled: 1,000 operations;
- random hit and random miss reads: 100,000 prepared keys and 100,000 reads;
- a scan returning the final 1,000 of 100,000 keys;
- serialized concurrent writes from 1, 2, 4, and 8 caller threads;
- synchronous batches of 1, 10, and 100 operations, totalling 1,000 writes.

TinyLSM also measures a synchronous full compaction of 100,000 entries prepared
with a 512 KiB MemTable threshold.

Google Benchmark v1.9.5 and LevelDB 1.23 are pinned by CMake FetchContent.
LevelDB compression is disabled. The sync flag is the same at the adapter
boundary, but the engines' lower-level durability implementations are not
identical on macOS.

## Pre/post result

The pre-V6 measurement was captured after adding only the benchmark harness and
before changing DB behavior. The post-V6 measurement includes crash-atomic
`WriteBatch` and one global mutex around public operations.

| Workload | Pre TinyLSM ops/s | Post TinyLSM ops/s | Change | Post CV |
| --- | ---: | ---: | ---: | ---: |
| Sequential write, async | 309,144 | 304,488 | -1.51% | 0.57% |
| Sequential write, sync | 50,268 | 47,270 | -5.97% | 8.01% |
| Random read hit | 18,460 | 18,486 | +0.14% | 0.08% |
| Random read miss | 5,130,617 | 5,313,367 | +3.56% | 10.72% |
| Scan final 1,000 | 23,255,814 | 22,242,982 | -4.36% | 7.54% |
| Full compaction | 619,662 | 620,676 | +0.16% | 0.11% |

The largest observed single-thread regression is 5.97%, but that synchronous
case is noisy. With only one before/after run, these values are a baseline and
not proof of a causal speedup or regression.

## New batch and concurrency measurements

| Workload | TinyLSM median ops/s | TinyLSM CV | LevelDB median ops/s | LevelDB CV |
| --- | ---: | ---: | ---: | ---: |
| Batch 1, sync | 43,857 | 22.32% | 248 | 0.34% |
| Batch 10, sync | 264,058 | 36.91% | 2,500 | 0.86% |
| Batch 100, sync | 611,418 | 6.46% | 25,082 | 0.51% |
| 1 caller thread, async | 451,880 | 2.03% | 696,534 | 0.96% |
| 2 caller threads, async | 343,502 | 21.35% | 431,338 | 22.78% |
| 4 caller threads, async | 217,455 | 8.92% | 348,694 | 1.28% |
| 8 caller threads, async | 196,943 | 0.80% | 264,179 | 0.33% |

Batching amortizes WAL sync and framing cost. TinyLSM's concurrency throughput
falls as callers increase because the implementation deliberately serializes
the complete operation with one mutex. This is the expected correctness-first
baseline for later lock-scope or read-concurrency work.

Do not interpret the macOS synchronous LevelDB numbers as a durability-adjusted
ranking. LevelDB's macOS environment performs stronger platform-specific sync
behavior than TinyLSM's current POSIX path, so this comparison does not isolate
engine efficiency. The asynchronous read/write comparisons are still useful as
directional profiling evidence, not as a fair product benchmark.

## Fixed Linux VM result

The Linux rerun is the primary same-machine TinyLSM/LevelDB comparison. Both
engines ran in the same process, against fresh directories on the same ext4
guest disk, with identical keys, values, operation counts, sync flags, and
randomized case ordering.

| Workload | TinyLSM median ops/s | TinyLSM CV | LevelDB median ops/s | LevelDB CV |
| --- | ---: | ---: | ---: | ---: |

| Sequential write, sync | 5,435 | 5.47% | 5,409 | 6.14% |
| Random read hit | 11,925 | 0.20% | 1,860,270 | 1.19% |
| Random read miss | 5,716,042 | 0.70% | 3,764,128 | 1.56% |
| Scan final 1,000 | 13,928,935 | 38.28% | 55,047,892 | 3.69% |
| Batch 1, sync | 5,401 | 3.65% | 5,557 | 9.54% |
| Batch 10, sync | 46,579 | 3.98% | 49,783 | 4.59% |
| Batch 100, sync | 202,441 | 16.83% | 229,568 | 15.67% |
| 1 caller thread, async | 674,634 | 1.07% | 1,615,059 | 2.97% |
| 2 caller threads, async | 432,868 | 3.01% | 695,146 | 5.59% |
| 4 caller threads, async | 253,867 | 1.84% | 301,584 | 3.14% |
| 8 caller threads, async | 225,362 | 1.49% | 298,705 | 1.78% |

TinyLSM full compaction reached 366,730 ops/s with 1.30% CV. TinyLSM is close
to LevelDB in the synchronous write cases on this VM, but substantially behind
on asynchronous writes, read hits, and scans. Random misses are faster because
the two engines have different lookup paths; that isolated result is not an
overall ranking.

Two complete runs are retained. The first started immediately after dependency
compilation at load averages 5.62/4.29/2.97; the rerun started at
0.44/2.50/2.51 and is the table above. Most medians were close across runs, but
TinyLSM Batch 10 changed from 25,413 to 46,579 ops/s. Scan and Batch 100 also
retain CV above 10% in one run. Treat these short sync and scan cases as noisy
baseline signals and increase operations/repetitions before using them as an
optimization gate.

The VM environment was Ubuntu 24.04.4 LTS ARM64, kernel 6.8.0-134, 4 vCPU,
8 GiB RAM, a 40 GiB ext4 disk mounted with
`rw,relatime,discard,errors=remount-ro,commit=30`, GCC 13.3.0, Clang 18.1.3,
CMake 3.28.3, and Ninja 1.11.1. The source snapshot identifies parent revision
`0f6e0347523978549454027f58ff1c2431238de6` plus the uncommitted goal changes;
its archive SHA-256 is
`c579d95b77501d5ac15138807b804bc9988fda3f2db8242817017f632316dd50`.

## Reproduce

Build and run all cases:

```sh
./run benchmark
```

Write machine-readable JSON while displaying only aggregates:

```sh
mkdir -p build/benchmark/results
./run benchmark -- \
  --benchmark_out=build/benchmark/results/run.json \
  --benchmark_out_format=json \
  --benchmark_report_aggregates_only=true \
  --benchmark_display_aggregates_only=true \
  --benchmark_enable_random_interleaving=true
```

## Correctness evidence for the measured revision

After the implementation and boundary test were added:

- Debug: 97/97 tests passed;
- AddressSanitizer + UndefinedBehaviorSanitizer: 97/97 passed;
- ThreadSanitizer: 97/97 passed with no reported data race;
- Release: configured and built successfully;
- formatting check, JSON validation, and `git diff --check`: passed after final
  documentation.

Coverage includes mixed legacy/single and version-2/batch WAL replay, corrupted
and truncated batches, append/sync fault injection, all-or-nothing MemTable
application, repeated keys, a batch crossing the flush threshold, reopen, and
eight concurrent callers.

## Fixed Linux VM deployment validation

The reproducible Lima definition pins the Ubuntu image URL and SHA-256, guest
architecture, vCPU, RAM, disk size, native guest filesystem, and packages.

Create and start the VM on an Apple Silicon Mac:

```sh
brew install lima
limactl start --name=tinylsm-linux --tty=false --progress --timeout=20m \
  tools/vm/tinylsm-linux.yaml
```

Copy a source checkout or exported snapshot into the guest disk, then run from
the guest project root:

```sh
./scripts/run_linux_baseline.sh
```

For an uncommitted local snapshot, the tested transfer pattern was to create an
archive that excludes `.git`, host build trees, and the independent Lab UI
submodule, copy it with `limactl copy`, and extract it below the guest home. Set
`TINYLSM_SOURCE_REVISION` and `TINYLSM_SOURCE_ARCHIVE_SHA256` when invoking the
script so `environment.txt` identifies that exported source exactly.

An optional output directory may be supplied as its first argument. The script
refuses to run outside Linux and preserves the source revision/status, OS, CPU,
memory, filesystem/mount information, compiler/tool versions, complete test and
build logs, benchmark log, raw JSON, and verifier output. It stops on the first
failed stage. The JSON verifier requires all 25 expected TinyLSM and LevelDB
median results, which also rejects a partial or skipped suite.

Acceptance requires all test configurations and the Release build to pass, no
sanitizer finding, and a complete JSON file without skipped benchmark cases.
Run at least twice; if a key case has CV above 10%, run again on an idle VM and
retain all raw files. Linux sync results, rather than the macOS sync comparison,
should become the primary durability-performance reference.

This run passed Debug, ASan/UBSan, and TSan at 97/97 tests, built Release, and
validated both 25-case JSON files. GCC 13 TSan could not start under this ARM64
VM because its runtime reported an unexpected memory mapping before `main()`;
the collection script therefore pins the race check to the installed Clang
18 runtime. The Clang TSan suite passed without a race report. A Release CLI
deployment smoke test created an ext4-backed database, wrote and reopened
`deployment=linux-ok`, read it, and scanned its Base64 JSON representation.

## Baseline limits and next measurements

This first harness measures aggregate wall time. It does not yet measure
per-operation p50/p95/p99 latency, peak RSS, write amplification, total disk
bytes, open/recovery time, long-running mixed read/write load, or datasets larger
than memory. Those should be added before choosing Bloom filters, block cache,
background flush, compaction policy, or finer-grained concurrency work. Profile
first; use this baseline to verify that each optimization changes the intended
cost rather than merely moving it.

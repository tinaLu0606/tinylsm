# 2026-09-04 · TinyLSM · Devlog

## V3 阶段三：内部 Iterator 与归并 Scan

状态：`已验证`

### 完成

- 新增仅供存储模块使用的 `InternalIterator`，统一 `Valid()`、`entry()`、
  `Next()` 和 sticky `status()` 合同。
- MemTable iterator 直接借用有序 map；SSTable iterator 使用 index 定位首个
  block，并且一次最多保留一个解码后的 data block。
- 新增拥有所有输入的 `MergingIterator`，按 byte-wise key 排序，为重复 key
  选择最大 sequence，并拒绝相同 key/sequence 的损坏状态。
- `DB::Scan()` 改为消费归并 iterator，过滤 tombstone；只有正常到达 EOF 才
  返回物化结果，后续 block 的 IO/CRC 错误不会产生部分成功结果。
- SSTable 单 block 读取现在同时核对 index 首尾 key 和非零 sequence，避免
  iterator 路径绕过已有数据校验。

### 测试

- 新增 MemTable 半开范围与 binary byte-wise 顺序测试。
- 新增多路归并 winner、tombstone、重复 sequence 和 sticky error 测试。
- 新增 SSTable 惰性跨 block 读取故障，以及 public Scan 不返回部分结果测试。
- Debug：`61/61` tests passed。
- ASan + UBSan：`61/61` tests passed；sanitizer 在实现过程中曾发现归并器
  current-group 容器复用问题，修正所有权表示后全量复验通过。
- clang-format、clang-tidy 和 `git diff --check` 通过；clang-tidy 仅保留仓库
  原有告警。

### 边界与下一步

- public `Scan()` 仍按既有 API 返回 `vector<Entry>`；惰性只存在于内部来源与
  归并阶段。
- 下一步复用同一归并 iterator 实现显式同步 full compaction。

## V3 阶段四：同步 Full Compaction

状态：`已验证`

### 完成

- public API 新增显式同步 `DB::Compact()`，合并全部 Manifest 已发布
  SSTable，不 flush MemTable，也不创建或切换 active WAL。
- compaction 复用内部 `MergingIterator` 的 winner 规则，只把 value 写入
  replacement SSTable；覆盖全部旧表后安全删除 tombstone。
- 输出全为 tombstone 时发布零表 Manifest，不创建空文件，也不消耗 file
  number；一张表允许重写。
- replacement SSTable 在 Manifest 提交前完成构建、同步、Reader 打开和
  metadata 校验；Manifest durable 后只执行 reader swap 与 noexcept
  best-effort cleanup。
- Manifest rename 可见但目录同步失败时沿用 terminal-state 合同，要求关闭并
  reopen；commit 前失败继续使用旧 Manifest/Reader 集合。

### 测试

- 覆盖零表、一表、多表、全 tombstone、MemTable/WAL 覆盖关系和重启等价性。
- 覆盖输入读取、replacement SSTable 构建/验证/rename、Manifest 写入/rename
  的故障矩阵，以及 Manifest visible-not-durable terminal 状态。
- 覆盖 commit 后旧表删除抛出异常仍保持 compaction 成功。
- Debug：`68/68` tests passed。
- ASan + UBSan：`68/68` tests passed。
- clang-format、clang-tidy 和 `git diff --check` 通过；clang-tidy 仅保留仓库
  原有告警。

### 边界与下一步

- 当前仍是调用方显式触发的同步 full compaction；没有后台、自动、partial 或
  leveled compaction。
- 下一步实现共享 filename parser 和 orphan cleanup，使提交前后遗留文件可以
  在当前进程或下次 Open 安全回收。

## V3 阶段五：Filename 与 Orphan Cleanup

状态：`已验证`

### 完成

- 新增共享 filename 模块，统一 Open、Flush、Compaction 和 Cleanup 使用的
  WAL/SSTable/临时 SSTable 格式化与解析规则。
- 编号 `1..999999` 左侧补零到六位，`1000000` 起自然扩展；parser 完整检查
  ASCII 十进制、非零、`uint64_t` 溢出和 format/parse round-trip。
- `DB::Open()` 仅在 Manifest、全部 SSTable 和 active WAL 完成恢复后执行
  cleanup；恢复失败时不删除现场。
- cleanup 只删除规范编号且不在 Manifest live set 中的 WAL/SSTable、所有规范
  `.sst.tmp` 和 `MANIFEST.tmp`；近似名称与无关文件始终保留。
- 删除失败会进入内存 pending 集合，由后续 Flush/Compaction 重试；重启后由
  Open 目录扫描重新发现。成功删除后 best-effort `SyncDir`。
- 文件系统故障注入新增 `ListDir`，cleanup 的列目录、删除、目录同步失败都不
  改变已经恢复或提交的数据状态。

### 测试

- 覆盖 `000001`、`999999`、`1000000`、`UINT64_MAX`，以及零、溢出、前导
  符号、空白、错误位数和近似后缀。
- 覆盖 active WAL/live SSTable/无关文件保护和 canonical orphan 删除。
- 覆盖 `ListDir`、`Remove`、`SyncDir` 故障不阻塞 Open，以及当前进程和重启
  后的删除重试。
- Debug：`76/76` tests passed。
- ASan + UBSan：`76/76` tests passed。sanitizer preset 会源码构建固定版本
  GoogleTest，避免与未插桩的系统静态库混用造成 libc++ 容器注解误报。
- clang-format、clang-tidy 和 `git diff --check` 通过；clang-tidy 对新增文件无
  项目代码告警。

### 边界与下一步

- cleanup 是正确性之外的空间回收；读取仍只信任 Manifest，不能依赖删除一定
  成功。
- 下一步执行跨模块故障矩阵、V0-V2 全量回归和最终 Release/sanitizer/lint
  门禁，并把 V3 状态收口为完成。

# 2026-09-07 · TinyLSM · Devlog

## 基本功能收口与性能基线

状态：`已验证`

### 已完成

- public DB handle 增加全局串行化保护，允许多个调用线程安全共享同一 handle；
  当前是 correctness-first 的单 mutex 边界，不代表并行执行能力。
- 新增 `WriteBatch`：多个有序 `Put`/`Delete` 编码为一条 version-2 WAL
  record，并共用一次可选 sync。恢复时完整 batch 整批应用，不完整尾记录整批
  丢弃；旧 version-1 单操作 WAL 仍可恢复。
- MemTable 支持 batch 一次性应用；覆盖 batch 内重复 key、跨 flush threshold、
  reopen、WAL append/sync 故障和损坏/截断恢复。
- 增加固定 Release benchmark，覆盖顺序写、随机命中/未命中读、尾部 Scan、
  Batch 1/10/100、1/2/4/8 调用线程和 full compaction；Google Benchmark
  `v1.9.5` 与 LevelDB `1.23` 固定版本。
- 安装 Lima 并创建固定 Ubuntu ARM64 VM；VM 使用 4 vCPU、8 GiB RAM、
  40 GiB ext4 guest disk，不通过 host shared filesystem 测量持久化路径。
- 保存 macOS pre/post、两轮 Linux 原始 JSON、Linux 环境记录、结果校验脚本和
  VM 定义；完整方法与限制见 `docs/performance/baseline-2026-09-06.md`。

### 验证证据

- macOS：`./run format --check`、`./run test`（`97/97`）、`./run release`、
  ASan/UBSan（`97/97`）和 TSan（`97/97`）通过。
- Linux：Debug、ASan/UBSan、Clang TSan 均为 `97/97`，Release 构建通过；
  两轮 JSON 均包含预期的 `25` 组 median。
- Linux Release CLI 在 ext4 上完成 Put、关闭后 Get 和 JSON Scan 的部署冒烟。
- GCC 13 TSan 在 ARM64 VM 中于 `main()` 前报告 unsupported unexpected memory
  mapping；改用 VM 内 Clang 18.1.3 后全套 TSan 通过。该问题记录为运行时/虚拟
  地址布局兼容性，不作为 TinyLSM data race。
- `git diff --check`、benchmark JSON 校验、shell 语法、YAML 解析及新增 C++
  文件 clang-format 检查通过。

### 基线表现

- macOS pre/post：全局 mutex 与原子 batch 加入后，已有单线程 workload 变化
  约为 `-5.97%` 到 `+3.56%`；当前样本不足以把变化归因为确定回归或提升。
- Linux rerun：TinyLSM async 顺序写约 `320,278 ops/s`，LevelDB 约
  `1,630,533 ops/s`；随机命中读约 `11,925` 对 `1,860,270 ops/s`；随机未
  命中读约 `5,716,042` 对 `3,764,128 ops/s`；尾部 Scan 约 `13,928,935`
  对 `55,047,892 ops/s`。
- Linux sync 单写两者接近，TinyLSM `5,435 ops/s`、LevelDB `5,409 ops/s`；
  Batch 10 为 `46,579` 对 `49,783 ops/s`，但短耗时 batch 的方差仍需注意。
- TinyLSM 1/2/4/8 caller async 分别为 `674,634`、`432,868`、`253,867`、
  `225,362 ops/s`。这符合全局 mutex 串行化的方向，但现有 workload 每线程固定
  10,000 次写，随线程数改变总数据量和 flush 次数，不能单独证明锁竞争成本。

### 分析与阶段决策

- `已验证`：原初版基本功能可以收口；持久化、恢复、batch 原子性、共享 handle
  正确性和可复现基线已形成闭环。
- `分析推断`：随机命中读远慢于随机未命中读，最可能的主因是命中路径需要反复
  读取并解码 SSTable block，而当前没有 block cache；应先用 profiler 和分层
  workload 验证，再实现缓存。
- `分析推断`：Scan 一次只测 1,000 条、Batch 总计只写 1,000 条，执行时间过短；
  Linux rerun 的 Scan CV 为 `38.28%`、Batch 100 CV 为 `16.83%`。这些 case
  适合作为方向性数据，不适合作为优化通过/失败门槛。
- `未做`：p50/p95/p99、peak RSS、磁盘写入量/写放大、Open/recovery 时间、
  超内存数据集和长时间混合读写。它们不阻塞进入性能阶段，但相关优化开始前应
  先补对应指标。
- `未做`：本轮代码、benchmark、原始结果和报告仍未提交。开始性能修改前应先
  建立独立 checkpoint，避免基线与优化代码混在同一变更中；提交需另行授权。

### 下一步

1. 在获得提交授权后，先将当前正确性实现与基线产物做 checkpoint。
2. 进入性能阶段的第一项不是直接改算法，而是稳定目标 workload 并采集 profile：
   优先拆分 MemTable hit、单 SSTable hit、多 SSTable hit、cold/warm block hit。
3. 若 profile 证实 block 读取/解码占主导，先实现有容量上限且可观测的 block
   cache；用随机命中读、Scan、RSS 和正确性回归验证收益与代价。
4. 在做并发、batch 或 Scan 专项优化前，分别固定总操作数/flush 条件并延长
   单次测量时间，降低方差后再建立对应 post-change 对比。

## Goal 1 · 读取 benchmark 与 Linux profile

状态：`已完成`

### 已完成

- 读取 benchmark 拆分为 MemTable hit、单 SSTable hit、四个重叠范围 SSTable
  的 oldest-table hit/in-range miss、256-key repeated hit、重复 Scan，以及固定
  40,000 总操作的 1/2/4/8 reader case。
- Scan 改为每次返回 10,000 条并重复 20 次；macOS harness run 的 median 为
  `5,077,660 ops/s`，CV 为 `0.59%`，不再使用旧的微秒级单次 Scan 作门槛。
- 固定 Linux VM 的基线源码哈希与主机一致。`perf cpu-clock` 随机命中读采集
  21,000 个样本且无丢失；`Crc32c` 占 `92.30%` self samples，主要调用链为
  `DB::Get -> SSTableReader::ReadBlock -> DecodeDataBlock -> Crc32c`。

### 决策与限制

- `已验证`：随机命中主要成本是每次重新读取、校验并解码 data block，因此进入
  有界 Block Cache 实现；不得通过关闭 checksum 获得提升。
- `已废弃`：旧 `ScanTail1000` 的进程级 profile 被未计时的数据准备主导，不能
  代表 Scan 热点；后续只 profile 延长后的重复 Scan。
- `环境限制`：Lima/VZ 不提供硬件 PMU，Linux profile 使用 `perf 6.8.12` 的
  software `cpu-clock` 与 DWARF call graph；不报告 cycles/instructions/cache-miss。
- Bloom Filter 暂不实现，等待新的 in-range miss 在 cache 后的残余成本证据。

### 当前验证

- `./run format --check` 与本机完整 Debug：`101/101` 通过。
- fixed-Linux Debug、ASan/UBSan、Clang TSan：均为 `101/101`；Release 构建通过。
- 两轮 before/after JSON 均通过 11-case 校验，全部目标 case CV < `10%`。
- ReadRandomHit profile 的 `Crc32c` 为 `92.30%` self samples；真实四 SSTable
  Scan profile 为 `87.25%`，两者都定位到 `ReadBlock -> DecodeDataBlock -> Crc32c`。
- 默认 8 MiB Block Cache 令 single-table hit 约从 `10.1k` 提至 `1.36M ops/s`，
  四表 in-range miss 从 `2.57k` 至 `670k ops/s`，四表 Scan 从 `1.08M` 至
  `8.83M ops/s`。其中 repeated hit 为 50,000 cache hit、0 decode；四表 Scan
  为 1,672 hit、88 miss/decode、2,139,664-byte charge。
- 共享读锁让固定 40,000 次 SSTable Get 从单读约 `1.17M ops/s` 扩展到 4/8 读约
  `1.84M ops/s`；它不是线性扩展承诺。

### 实现与边界

- cache 只在 CRC、结构与 sequence metadata 全部验证后插入；disabled、失败读取、
  LRU charge 上限、compaction 旧 table 清除及并发读重叠都有覆盖。
- `Get`、`Scan`、diagnostic snapshot 使用 shared lock；写入、Compact、Close 使用
  unique lock。Scan materialize 期间会阻塞 writer。
- Bloom Filter 不实现：cache 后 negative lookup 的残余路径不再是 decode/CRC
  hotspot，现有数据不支持新增 persistent metadata。
- 详细方法、限制、RSS 与完整原始 JSON 位于
  `docs/performance/read-path-2026-09-07.md`。
